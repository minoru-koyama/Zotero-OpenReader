## A one-letter word gets a point CFI in an EPUB, so its word position shows no text (2026-11-01 00:03, issue #209)

Seen on the 1.16.16-beta5 run of `breaks-and-images`: with a word-timed
voice (Fish Audio), `highlight: word position shows the wrong text and no
rewrite fixes it` was written once, at the first word of the EPUB fixture's
paragraph 6, "A". Zotero 10.0.6 `resource/reader/reader.js:62321-62353`
(`resolveSelectorMap`, `resolveMultiEntry`) writes a one-character span as
a point, `epubcfi(<path>:<offset>)`, not a range; `toDisplayedRange` gives
an empty range, so the text check fails and the plugin paints the primary
transparent for that word. Zotero itself would draw nothing for the empty
range either. Every one-letter word in an EPUB ("A", "I", "a") meets it;
the snapshot's stream range for the same word shows "A". It is older than
#209: the check compared the empty `toString()` before the fix as after
it. `zotero-tester` replayed the word rule over all 72 word timestamps the
Engine held for the fixture: this was the only failing word, and the alt
text's words in paragraphs 4 and 5 have no source position at all, so they
are neither checked nor drawn.

## Zotero's EPUB resolver gives a point no end, and the snapshot view appends two `<div>`s after the page's last block (2026-11-01 00:55, issues #235, #236)

Measured live on 1.16.16-beta5 and Zotero 10.0.6 with the
`breaks-and-images` fixtures (the research run on #235 and #236), and
replayed offline over the owner's library.

- **A point CFI resolves to an empty range.** `EPUBView.toDisplayedRange`
  (`reader.js:57814-57840`) goes through `EpubCFI.toRange` (`47006`):
  for a CFI that is not a range (`cfi.range` false, `47022`) only the start
  is resolved (`47030`, `setStart` at `47039`); `endContainer` (`47010`)
  is never assigned, so `setEnd` (`47054`) is skipped and the range stays
  collapsed: `toString() === ''`, one client rect 0 wide. Zotero writes a
  point for every span of exactly one character (`resolveSelectorMap`
  `62321-62340`, `resolveMultiEntry` `62341-62361`), both for the word
  position (`InternalReader._computeActiveWordSourcePosition`,
  `83977-83985`) and for a Segment's own position
  (`EPUBPositionMapper.textNodeSpansToSourcePosition`, `62521-62536`). The
  same span as a range, `epubcfi(P,:o,:o+1)`, shows the character. So
  Zotero's own player draws nothing for "A" either.
- **Zotero builds points on purpose too.** The follow's
  `_collapseToStart` (`53398-53407`) collapses a Segment's range to its
  start and turns it back into a selector to scroll to. A point is
  therefore not always a one-character span; the plugin widens one only
  where it knows the text it must show (`repairSelectorForText`).
- **The snapshot's live body is longer than the source's.** The view
  appends `div#annotation-overlay` (`view._annotationShadowRoot.host`,
  `53721-53725`) and Read Aloud's jump button (`view._readAloudJumpButton._el`,
  created at `53734`, appended at `44897`) after the source's children, and
  prepends nothing. A Segment's `CssSelector` comes from the snapshot
  mapper, `_streamRangeToSelector` (`63134-63161`) →
  `generateDomMapSelector` (`62831`) → `domMapSegment` (`62854-62872`), on
  flags the document worker computed from the source (`buildDomIndex`,
  `worker.js:166654` on). `SnapshotView.toDisplayedRange`
  (`60569-60609`) resolves it with `body.querySelector` on the live page,
  so `body > p:last-child` (and a `div:last-of-type`) misses.
- **How often, in the owner's library.** 62 English EPUBs, 38.5 million
  words: 3.5% of words are one character, 41% of sentences hold one
  (per book: 36% / 43% / 60% at the 10th / 50th / 90th percentile). 86
  snapshots, Zotero's naming replayed with htmlparser2 and two `<div>`s
  appended: 9 have text under a step that no longer resolves (8
  `div:last-child`, 1 `div:last-of-type`, 1 `blockquote:last-child`),
  none more than 25% of its page's text.

The fix (1.16.16-beta6) adds both shapes to `repairSelectorForText`: a
point becomes the one-character range, then goes through the text-step
rewrites; a `body > x:last-child` / `:last-of-type` is counted back as
`:nth-last-child(k)` / `:nth-last-of-type(k)`, k up to 5, its
`TextPositionSelector` kept. Each is kept only when it shows the text
being read. Word level only: at Sentence only Zotero draws its own Segment
position, and a one-character Segment or a snapshot's last block stays
undrawn there.

## Zotero 10.0.7 calls clearFailures before Play, and the Engine controller lacked it (2026-11-01 15:52)

Reported on Zotero 10.0.7 with both local Kokoro and MLX Audio Qwen3-TTS:
`TypeError: this._controller.clearFailures is not a function`. Replayed
the installed `resource/reader/reader.js`'s `ReadAloudManager.play`
(`82608-82620`) against `createEngineController`: the exact exception
occurs before the controller is unpaused. The regression is independent
of the speech provider. No public issue was opened, at the user's request.

The native controller's `clearFailures` (`40287-40293`) clears every failed
index and, only when an error is present, clears it and emits
`ErrorCleared`. It does not resume audio. The Engine now exposes the same
operation through its reader-window controller, delegated to the session;
retired controllers and ended sessions remain inert. `retry` retains its
existing current-sentence behavior. A no-op would remove the exception
but leave Play unable to recover a failed sentence.

The integration harness remains pinned to the verbatim Zotero 10.0.3
fixture; the resume test now exercises the newer controller call before
Play, and an error-recovery test checks that clearing is idempotent, does
not fetch or start audio by itself, and allows Play to fetch the failed
sentence again. Both failed before the fix with the missing-method error.

Runtime smoke: executed the installed Zotero 10.0.7 `play` method with the
real Engine, controller adapter, Web Audio output and local provider
implementations in Chromium, muted at the plugin's gain. For Qwen
(`mlx-community/Qwen3-TTS-12Hz-0.6B-CustomVoice-8bit`, `Ryan`) and Kokoro
(`af_heart`), an injected first network failure recovered on Play, followed
by a successful pause/resume. Each made two fetch attempts, emitted one
`ErrorCleared`, and reached a running 48 kHz AudioContext. This proves
the native Play call and real audio path outside Zotero, not its reader
compartments or visible controls. The running Zotero still needs the
user to install the corrected `1.16.16-beta7` XPI and verify there.

## Disabled provider switches do not unload the external model servers (2026-11-01)

The user observed disabled providers in the diagnostic profile and two
Python processes with substantial memory use. The provider switches had
been enabled for the earlier playback research, then restored during
cleanup. Those switches control OpenReader requests, not the independent
launchd services or their retained models. The servers remained running
throughout the isolated checks.

`lsof` identified PID 83529 as the MLX Audio/Qwen server on loopback port
8000 and PID 83691 as native Kokoro-FastAPI on loopback port 8880. Both
sampled at zero CPU usage. Resident-set size was small and did not capture
the substantial memory charged to these processes. Targeted
`footprint --noCategories -f bytes -p 83529 -p 83691` reported:

| Server | Current footprint (GiB) | Peak since process start (GiB) |
| --- | ---: | ---: |
| MLX Audio / Qwen | 2.74 | 8.16 |
| Kokoro-FastAPI | 1.82 | 2.40 |
| Combined current footprint | 4.56 | — |

The individual peaks must not be added as a simultaneous measurement.
Footprint is the process's charged memory, not a promise that stopping it
will release that exact amount of currently resident physical RAM.
`sysctl` reported approximately 10.66 GiB of swap in use and
`kern.memorystatus_vm_pressure_level: 2`. Apple's
[memorystatus documentation](https://github.com/apple-oss-distributions/xnu/blob/main/doc/vm/memorystatus_notify.md)
describes elevated pressure as a reason to relax caching.

Resource pressure is a credible investigation path, but these readings
are current, not measurements captured during the original native crash.
Successful isolated checks already ran with these servers present, so
their presence alone does not reproduce the failure. No service was
stopped or autostart setting changed for this measurement. A temporary
service stop and before/after pressure comparison would need to preserve
the user's choice about local voice availability.

The user selected a temporary stop of both servers. `launchctl bootout`
unloaded only `gui/501/local.openreader.mlx-audio` and
`gui/501/local.openreader.kokoro`. Both original PIDs disappeared, and
`lsof` found no listener on ports 8000 or 8880. No model files or
LaunchAgent plists were removed or edited.

| Measurement | Immediately before stopping | Five seconds after stopping |
| --- | ---: | ---: |
| `kern.memorystatus_vm_pressure_level` | 2 | 1 |
| Swap in use (GiB) | 10.45 | 10.43 |

The pressure reading decreased after the servers exited. This supports
the user's resource-pressure concern, but does not establish the cause
of the earlier Zotero crash: the original freeze still lacks a

## Normal startup recovered after our retained read-only SQLite inspection was closed (2026-11-01)

The user reported the normal Zotero window stuck behind its startup
overlay, with no entries visible but Settings accessible. This is a new
observed symptom, distinct from the earlier native crash. Read-only
add-on metadata showed only zotxt, ZotMoov and Better BibTeX active:
OpenReader was not installed in the normal profile.

`lsof` identified normal Zotero PID 60786 and our persistent Python Eval
PID 9845 as owners of the normal `zotero.sqlite`. The Python connection
was retained from the earlier authorized attachment-path query.
The before-release sample,
`/tmp/openreader-normal-startup-60786.sample.txt:1158-1181`, showed the
database worker repeatedly in `sqlite3_step` and `fcntl`, while the main
thread continued processing its event loop. The memory-pressure sysctl
was 1 during the stall, after the model servers had been stopped.

The Python connection reported `in_transaction: False`. We closed only
our associated cursors and that read-only connection, without writing
to the database. `lsof` then showed only Zotero owning the database.
In `/tmp/openreader-normal-startup-after-inspection-close.sample.txt:1052-1062`,
the same database worker was idle in its condition-variable wait.
The user then confirmed that all entries appeared, without restarting
Zotero or repairing its database.

This strongly implicates our retained inspection connection/cursor as
the blocker for this startup stall. An explicit transaction flag is not
sufficient evidence that a reader holds no lock. Future Python SQLite
inspection must finish and close cursors and close the connection in a
`finally` or `contextlib.closing`; `with sqlite3.connect(...)` alone is
only transaction management, not connection cleanup. No connection to
the live normal library should remain retained in an Eval kernel.

This recovery does not establish the cause of the earlier beta7 native
crash, and must not be presented as a second plugin fix. No further
normal-profile restart, reinstall or database repair is warranted for
the recovered startup stall.

- **Build identity.** `1.16.16-beta8` in `addon/manifest.json`
